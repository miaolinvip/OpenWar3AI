# OpenWar3 架构

> 目标（来自项目发起人）：
> 1. 用这一个目录里的代码，就能把现有功能全部跑起来；
> 2. 在用的大脑和决策放在一个目录；
> 3. 分析出来的所有操作接口、信息接口都做成外部能方便调用的形式，延迟要特别低；不懂代码的人可以让 AI 照着接口写一个陪玩 AI；
> 4. 以后不同玩家用自己设计的 AI 互相对战，比谁的 AI 厉害。

---

## 1. 分层总览

```
┌──────────────────────────────────────────────────────────────────────────┐
│  War3.exe（1.27，未修改）                                                 │
│   └─ render_hook.dll（native/，启动器注入）                               │
│        · 状态发布器：每 50 ms 把全图写进世界块 War3World + 事件环（W3P）   │
│        · 快车道：在游戏线程上成批执行客户端提交的调用                      │
│        · 画板 / 输入：画在鼠标指针下面；接管窗口过程报点击、热键           │
│        · 控制通道：老的「一个请求等一次消息泵」路（兼容、界面类操作）      │
│        · 读线程：纯 memcpy，不等游戏线程                                   │
└──────────────▲──────────────────────▲────────────────────▲───────────────┘
               │ 共享内存（零拷贝）    │                    │
┌──────────────┴──────────┐ ┌────────┴─────────┐ ┌────────┴───────────────┐
│ sdk/python（接口层）      │ │ console/ 远见     │ │ director/ 导播          │
│  w3world  世界+事件（读）│ │ 网页指挥台 8866   │ │ speech/ 头顶气泡 8872   │
│  w3fast   快车道（写/读） │ │ 起停实例、看大脑  │ │（观赏层，不影响胜负）   │
│  w3canvas 画板            │ └──────────────────┘ └────────────────────────┘
│  w3input  输入            │
│  w3chan   控制通道（兜底）│
│  w3cmd    已验证的配方    │
│  w3claim  统一仲裁表      │
│  openwar3 门面：Game/Bot  │◄── 对外唯一稳定接口（docs/API_ZH.md 自动生成）
└──────────────▲───────────┘     gateway/ 网关 8870（WebSocket/JSON，任何语言、浏览器）和
               │                 tools/war3_mcp.py（MCP，大模型直接调工具）都架在门面上
               │ import
┌──────────────┴──────────────────────────────────────────────────────────┐
│ brains/（决策层 —— 所有"AI 怎么想"都在这里，接口层不含任何策略）          │
│   xwar3/strategy   参考大脑：AMAI 式战略 + 建造表 + 战术（3 s 级）        │
│   xwar3/reflex     毫秒层：保命、施法、集火、捡装备（100 ms 级）          │
│   xwar3/worldmodel 胜率模型（推理子集）                                  │
│   examples/        hello_bot / rush_bot：写新 AI 的起点                   │
└─────────────────────────────────────────────────────────────────────────┘
runtime/farm.py —— 多实例编排（拷 War3-<N>.exe、启动器、每局重开）
```

**分层的唯一规则：下层不知道上层存在。** 接口层（sdk）里没有一行"该不该打"的逻辑；
大脑之间不互相 import（参考大脑和示例 bot 都只依赖 sdk）。这就是对战平台能成立的前提 ——
平台只需要"接口层 + 裁判"，谁的大脑都能插上来。

## 3. 低延迟：为什么是"快车道"，而不是"全部塞进 DLL"

### 3.1 慢在哪（实测，不是猜）

旧的控制通道每个请求：抢**全机共用**的互斥量 → `PostThreadMessage` → **等游戏下一次取消息**
（War3 一帧取一次，16~33 ms）→ 等 done 事件 → 放锁。实测 20~40 ms/次；
参考大脑 93% 的墙钟在等它，每分钟稳在约 2000 次 = 被通道吞吐卡住。

**跨进程本身不慢**：共享内存读写是纳秒级，快照读一份约 0.05 ms。慢的是"一个请求等一次消息泵"和"全机一把锁"。

### 3.2 快车道（已实现，客户端在 `sdk/python/w3fast.py`）

* DLL 建 `Local\War3Fast_<pid>`：16 条车道 × 16 个槽（09-23 从 8 条扩到 16：大脑 + 4 个毫秒层 + 网页 + 导播 + 气泡就占满了 8 条），
  一个客户端对象独占一条车道 → **不加锁**（每个槽一个写者一个读者，x86 的写顺序就够）。
* 在游戏线程上执行，每秒数百次。没有提交时的开销 = 8 次整数比较。
* **成批**：一次提交 16 条命令，同一次分发里全部执行（旧通道要 16 × 30 ms）。
* **时间预算** 4 ms/次：做不完的留给下一次分发，不会拖住游戏。
* **截止时间**：游戏暂停时车道不排空，客户端超时后退回控制通道；过了截止时间的槽 DLL 只标过期、不执行 ——
  不会出现"暂停恢复后旧命令又执行一遍"。
* 快车道上只跑语义命令（移动、攻击、建造、查询、镜头、JASS……），客户端不需要知道任何游戏内部结构。

### 3.3 五档接口（按延迟）

| 档 | 通道 | 延迟 | 谁用 | 状态 |
|---|---|---|---|---|
| 0 | 推送式世界状态 + 事件流（W3P，读） | 读一份 ~0.4 ms；数据每 50 ms 新一份（可调到 16 ms） | 所有 bot | ✔ 09-23 实机 |
| 1 | 快车道（调用/订单/读对象） | 落在事件簇里 ~0.1 ms，否则等下一帧（P95 ~15 ms） | SDK 默认 | ✔ 09-23 实机：6 进程并发中位 67→0.06 ms、吞吐 88→3000 次/秒；16 条一批 13 ms（逐条 121 ms） |
| 2 | 控制通道 | 20~40 ms | 兜底、界面类操作（镜头、HUD） | ✔ 已验证 |
| 3 | 网关（WebSocket/JSON） | 档 1 + ~1 ms | 任何语言、大模型、远程对战 | ✔ 09-25 `gateway/server.py`（`docs/GATEWAY_ZH.md`）；对战裁判仍是设计（§5） |
| 4 | 进程内插件（DLL 在游戏线程里直接调） | 微秒 | 只给本机可信代码 | 不建议做（见下） |

**为什么不把大家的 AI 都做成 DLL 塞进游戏（档 4）**：
1. 延迟收益很小 —— 档 1 已经是"一帧内落地"，而游戏本身按帧推进，再快也要等下一帧才有效果；
2. 一个 bot 的空指针 = 整局游戏崩溃（外部进程崩了只是那一方空过）；
3. 对战时无法限制它：进程内代码能直接读写对手的一切、能改游戏，裁判形同虚设；
4. 逼作者写 C/C++，和"不懂代码的人让 AI 写"正好相反。

所以对外形态是：**一个 DLL（我们的，负责注入和执行）+ 任何语言的外部 bot 进程**。
"直接启动魔兽就能加载"由启动器完成：`tools/play.py --bot 你的bot.py` 一条命令起游戏、注入、开局、拉起 bot。

### 3.4 还能再快的地方

已做：英雄蓝量 / 冷却 / 订单目标 / 背包都在世界块里（09-23 W3P，读一份 ~0.4 ms，不用再走档 1）；
发布周期客户端可调（16~1000 ms）；批量下令 `with g.batch():` 一批只等一次游戏线程。

没做：
1. **按游戏 tick 发布**：现在按固定周期；倍速下可以更密。

## 4. 决策层（brains/）约定

一个"大脑"就是一个进程，只 import `sdk/python`：

```python
from openwar3 import Bot, run
class MyBot(Bot):
    def on_tick(self, g): ...          # g 是 Game：snapshot()/units()/move()/attack()/cast()/train()/build()...
run(MyBot, inst=5)
```

* 参考大脑 `brains/xwar3` 是"策略层 + 毫秒层"两级，毫秒层是 4 个独立进程；它们通过 `w3claim` 仲裁表共享单位
  （优先级：人手 95 > 保命 90 > 躲技能 85 > 施法 80 > 捡装备 70 > … > 策略 50 > 派工 45）。
  新 bot 在表里的身份是 `bot`（id 7），默认优先级 50。
* 一局一个 bot 进程是最简单的形态；要多个进程协作（像参考大脑那样），就都走仲裁表。

## 5. 对战平台（让不同玩家的 AI 互相打）

详见 `docs/ARENA_ZH.md`。结论先说：

**公平只能由裁判保证，不能靠 bot 自觉。** 注入进游戏的客户端能读到全图（这是本项目观察能力的来源），
所以"每人在自己机器上跑一个 War3 + 自己的 bot，走局域网对战"**无法防止读全图** —— 这种模式只适合友谊赛。
正式比赛用**集中式裁判**：

```
            ┌────────── 裁判机（可信）─────────────────────────────┐
 bot A ─WS─►│ 网关：鉴权 → 按 A 的视野过滤观察 → 校验命令只动 A 的单位│──快车道──► War3（一局，A、B 两个槽）
 bot B ─WS─►│        → 每拍命令/时间预算 → 记录每条命令（可回放）   │
            └─────────────────────────────────────────────────────────┘
```

* bot 只能看到网关给的、按自己视野过滤过的观察（`visible()` 就是这个用途），只能提交动作，永远碰不到共享内存；
* 网关用快车道替每个槽下令，**每条命令先校验单位归属**（归属由平台自己校验，不依赖引擎）；
* 节拍按**游戏时间**：每 N 游戏毫秒给所有 bot 一份观察，截止前没交的视为空过 —— 慢 bot 自己吃亏，不拖别人；
  需要严格公平时开"锁步"：发观察时暂停游戏、收齐（或超时）再继续，机器快慢不影响结果。

### 地基实验（按顺序，前一条不过不做后一条）

| # | 实验 | 为什么 | 已知 |
|---|---|---|---|
| 1 | 一局里开 2 个槽，都不带内置 AI | 否则电脑 AI 会和 bot 抢指挥 | 启动器已能按槽写种族 / 难度；关掉槽上内置 AI 的办法有实测线索 |
| 2 | 替**非本机玩家的槽**下令 | 裁判要替两边下令 | 替别的槽下令的行为待实测；归属由平台自己校验 |
| 3 | 按玩家过滤视野 | 公平观察 | `IsVisibleToPlayer`（JASS native）接受任意玩家号 |
| 4 | 程序化判胜负 | 批量天梯 | 现在靠"对方没建筑"；事件流里的 `player.left` / `game.ended` 更直接 |
| 5 | 锁步暂停/继续 | 严格公平 | `PauseGame`（JASS native）已验证；回放里 `PauseGame(0)` 不恢复 |

## 6. 硬性约束（不变）

只用于本机、离线、局域网、自建游戏；不用于 Battle.net，不与 Warden 活跃会话一起用；
**不修改磁盘上的 Game.dll**；多开只是把原版 `War3.exe` 启动壳原样拷贝改名。
