# 对战平台设计：让不同玩家的 AI 互相打

> 前身是 08-27 的设计稿。这一版吸收了之后一个月的实测：
> 快车道、统一仲裁、视野查询、下令的归属校验、电脑 AI 的队长逻辑等。

## 1. 三种形态，按"公平能不能保证"排

| 形态 | 怎么跑 | 公平 | 适合 |
|---|---|---|---|
| **A 本机擂台** | 一台机器一局 War3，bot 各占一个槽，裁判进程替它们下令 | 裁判控制一切：视野、归属、节拍 | 开发调试、本地联赛 |
| **B 托管天梯** | A 搬到服务器；玩家上传 bot 代码（Python），服务器在沙箱里跑 | 同 A，再加代码隔离 | 公开比赛、排名 |
| C 各自联机 | 每人自己机器跑 War3 + bot，局域网对战 | **不能保证**：注入的客户端能读全图 | 朋友之间的友谊赛 |

**建议先做 A，同一套协议直接升级到 B；C 只当娱乐。**
原因很简单：本项目观察能力的来源正是"客户端持有全部玩家的状态"，这对自己的机器同样成立 ——
没有任何办法阻止一个人在自己机器上读全图。公平只能来自一个**大家都信任的裁判**。

## 2. 形态 A 的组件

```
┌ Arena 裁判（arena/，待写）──────────────────────────────────────────────┐
│  编排：选图、开局（启动器 --race/--difficulty 已能按槽写种族/难度）       │
│  节拍：每 T 游戏毫秒一拍（默认 200）；锁步模式下发观察时暂停游戏          │
│  观察：快照 → 按每个槽的视野过滤（IsVisibleToPlayer，任意玩家号）→ JSON   │
│  动作：校验「单位属于这个槽」→ 预算（每拍 N 条、APM）→ 快车道批量下达     │
│  记录：每拍观察摘要 + 每条动作（可回放、可复盘、可做训练数据）            │
│  判定：某槽没有建筑 → 出局；超时 → 按剩余战力/资源判                    │
└──────────────▲──────────────────────────────▲───────────────────────────┘
        WebSocket（JSON）                WebSocket（JSON）
        bot A（任何语言）                 bot B（任何语言）
```

bot 永远不接触共享内存和 DLL。作者用 `openwar3` SDK 写的 bot，只要把 `Game` 换成 `ArenaGame`
（同名方法，底下走 WebSocket）就能上擂台 —— **接口层的抽象就是为此设计的**。

## 3. 协议草案（v0）

每拍裁判发：
```json
{"t": "obs", "tick": 57, "gameMs": 11400, "me": 1,
 "res": {"gold": 320, "lumber": 150, "food": [18, 30]},
 "units": [{"id": 101, "type": "hfoo", "owner": 1, "x": -4500, "y": 2200, "hp": 380, "hpMax": 420, "order": "attack"}],
 "visibleEnemies": [{"id": 733, "type": "ogru", "owner": 2, "x": -3900, "y": 2500, "hp": 700}],
 "deadlineMs": 180}
```
bot 回：
```json
{"t": "act", "tick": 57, "actions": [
  {"do": "attack", "unit": 101, "target": 733},
  {"do": "train", "unit": 5, "code": "hfoo"},
  {"do": "cast", "unit": 7, "spell": "thunderbolt", "target": 733},
  {"do": "move", "unit": 102, "x": -5000, "y": 2000}]}
```
* `id` 是裁判分配的稳定编号（不是内存地址 —— 地址会复用，也不该暴露给 bot）；
* 动作集合 = `docs/api.json` 里 `category == "command"` 的那些，参数同名；
* 迟到的 `act` 丢弃，这一拍视为空过（单位继续执行手上的命令）。

## 4. 必须先做的地基实验

| # | 实验 | 判据 | 已知线索 |
|---|---|---|---|
| 1 | 开一局 2 个槽都没有内置 AI | 两边单位都不动 | 启动器已能按槽写种族 / 难度；关掉槽上内置 AI 的办法有实测线索 |
| 2 | 替**本机以外**的槽下令 | 敌方槽的农民真的去采矿 | 替别的槽下令的行为待实测；归属由平台自己校验（见上面「动作」一行） |
| 3 | 按任意玩家号查视野 | 同一点对两个槽给出不同结果 | JASS native `IsVisibleToPlayer(float*, float*, player)` |
| 4 | 程序化判胜负 | 一方建筑全灭时 1 秒内知道 | 参考大脑的 `classify_end`；事件流里的 `player.left` / `game.ended` |
| 5 | 锁步 | 暂停中收齐动作、恢复后生效 | `PauseGame`（JASS native）已验证 |

第 2 条是整条路的地基：不过，就只能退到"每个 bot 一个 War3 客户端，走真联机"（形态 C 的技术路线，但裁判仍可在主机侧校验）。

## 5. 公平规则（默认值，可按赛制调）

* 观察只含**我方单位 + 我方视野内的敌方单位**；野怪、金矿按视野或开局公开；
* 每拍最多 32 条动作；超出的截掉（防刷命令拖慢裁判）；
* 同一单位同一拍只认最后一条；
* bot 计算时间预算 = 拍长 × 0.9，超时空过；
* 同一对 bot 双方各打一次（交换出生点），消除地图不对称；
* 天梯：Elo / TrueSkill，每对至少 20 局再下结论（本项目实测：2 局能看出的最小胜率差约 60 个百分点）。

## 6. 和参考大脑的关系

参考大脑 `brains/xwar3` 现在直接用 sdk 底层（w3cmd/act），并且读全图。上擂台需要：
1. 换成门面接口（`Game`）；
2. 所有"看敌人"的地方只用视野内的单位（它现在大量依赖全图信息，比如电脑队长的目标点）。
这正好是一次检验：**离开全图信息，它还剩多强。**
